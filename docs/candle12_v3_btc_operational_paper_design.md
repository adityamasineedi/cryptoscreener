# Track 2: CANDLE12_V3_BTCUSDT_1H_OPERATIONAL_PAPER (design only)

**Status:** DESIGN_ONLY. Nothing has been implemented or started. Implementation and start each need the user's approval.

**Disclosure:**
- **This BTC operational track does not validate strategy performance** and never counts toward OOS.
- **OOS-2 remains the formal blind BTC test.** Every outcome field stays sealed until its read on or after 2027-10-16.
- **ETH (Track 1) is a separate, correlated research book.** This track never reads it.

## 1. Decision needed: how Track 2 gets its BTC execution data

**A separate runner would in effect be a second OOS-2 runner.** Suppose Track 2 ran its own BTC 1h virtual-paper runner on the frozen rules. It would see the same bars and run the same code, so it would produce **the same trades as OOS-2**. That conflicts with the decision's own rule, "do not create a second BTC OOS-2 runner". It would also:
- create a second store holding exactly OOS-2's sealed outcomes, doubling what must be protected;
- add a resident process on a constrained machine;
- check a copy of the execution path, not the one that counts.

| Option | What it is | Recommendation |
|---|---|---|
| **A (recommended): operational track over OOS-2's records** | Track 2 is the CANDLE12_V3_OPERATIONAL_VIEW (`docs/candle12_v3_operational_view_design.md`, commit 3fda2e4), extended as in section 3. It reads only allow-listed fields of the **real** OOS-2 execution path. It has its own contract, records, dashboard and bounded task, and runs no second runner. | **Recommended.** It verifies the path that actually counts, at a fraction of the cost. |
| B: separate BTC runner, sealed store | A second frozen-rules BTC virtual runner with its own store, shown only through the allow-list below | **Not recommended.** It is a second OOS-2 runner in substance. It would need the user's explicit override of "no second runner". |

The rest of this document specifies Option A. If the user chooses B, the same allow-list, cadence and tests apply to B's store, plus a resident-process budget of BelowNormal and ≤ 250 MB.

## 3. Dashboard: allowed fields

The dashboard is a static HTML page plus `report.json`, generated by `opsview.py` into `backend/data/candle12_v3_paper/operational_view/` (its own folder; nothing written to OOS-2).

| Field | Source (allow-listed) | Cadence |
|---|---|---|
| Latest processed bar, processing delay | `state.json` `last_closed_time`, `saved_at` | each run |
| Heartbeat age, halted, kill switch | `heartbeats.jsonl` `at`, `halted`, `kill_switch` | each run |
| Runner up, restarts | `runner.lock` pid and refresh; `ADAPTER_RESUMED` / `RUNNER_CRASH_RECOVERED` counts | each run |
| Signals detected | count of `SIGNAL_DETECTED` events (kind and time only). The blocked / missed / no-fill split is **sealed**, because blocked counts track time in position. | weekly snapshot |
| Orders: requested / accepted / rejected (by reason) / canceled / filled | event kinds | entry orders: weekly snapshot. Exit orders: weekly totals only (path-identical under `nearest_target_full_exit`: 2 placed, 1 filled, 1 canceled per trade). |
| Reconciliation pass/fail | in-memory replay (view design §5): pass/fail per category, exception type. Exit checks report only "within tolerance: N of M". | weekly snapshot |
| Fill-deviation statistics | entry fills: mean and max deviation (bps). Exit fills: pass/fail only, no magnitudes. | weekly snapshot |
| Funding coverage | every settlement since the window start present in the feed and the database (yes/no), plus the `MISSING_FUNDING_DATA` count. Not tied to positions; no amounts. | each run |
| Exceptions and alerts | `exceptions.jsonl` id / category / status / times; `alerts.jsonl` kind / at | each run |
| Fingerprint and tree | `guard.fingerprint_status()`; contract paths clean | each run |
| Store integrity | sequence numbers contiguous, no torn lines (checked on allow-listed files only), duplicate suppressions | each run |
| Backup | **No OOS-2 store backup exists today.** Shown as "NOT CONFIGURED" until an optional backup is approved (section 7). | each run |

**Why weekly snapshots.** The view design shows lifecycle counters without times. But anyone who polls them every hour could rebuild **when each trade closed**, from exit fills ticking up and from new entries (one position at a time), and so recover holding times, which are sealed. This track therefore updates every trade-lifecycle counter (signals, orders, reconciliation, deviations) only from a snapshot taken Monday 00:00 UTC, and labels it "as of". Health fields stay real-time. **This tightens the view design's section 4 and corrects a gap in it.**

**Residual exposure:** some exception categories (for example `EXIT_ORDER_FAILED`) are shown in real time because operations needs them. Their timing can reveal that an exit happened. They are rare, and this is disclosed.

## 4. Sealed until the formal read

These fields are never shown before the formal read:
- trade PnL, R, equity;
- win/loss count;
- exit reason (STOP vs TARGET) and stop-fill vs target-fill counts;
- exit price, exit time, exit slippage sign and magnitude;
- per-trade funding;
- fee totals;
- position open/closed state over time and holding time;
- the blocked-signal split;
- anything else that reveals whether a trade won or lost.

**Never opened:** `trades.jsonl`, `signals.jsonl`, `reconciliation.json`, `oos_reads.jsonl`, `state.json.tmp`. The `slots` field in `state.json` and in heartbeats is never parsed.

**Rule enforcement:** the parser fails closed, as in the view design §2. Every run is recorded in `access_log.jsonl`.

## 5. Reconciliation (purpose-blind)

The checks match Track 1 and OOS-2's frozen tolerances:
- entry, stop and target fill within 0.05%, unless a documented gap event;
- quantity exact after step rounding;
- fees within $1e-6;
- funding within $1e-9 of the exchange-reported rate × notional;
- exit reason and PnL/R recomputed.

Every comparison runs **in memory only**. What leaves the process:
- pass/fail by category;
- the exception type;
- entry-deviation aggregates;
- the count of unresolved exceptions.

**Not run during the window:** the frozen `reconcile` CLI. It writes full per-trade detail into the OOS-2 store.

**Escalation:**
- a failed category → owner review by category;
- 2 or more failures of one category within 7 days → the OOS owner;
- a failure that can't be diagnosed blind → break-glass only, with written user approval. It is disclosed with the OOS-2 result.

## 6. Isolation, process and budget

**Never read:**
- Track 1's ETH store;
- LCSC files;
- any OOS-2 field outside the allow-list.

**Never written:** OOS-2, the fingerprinted files, shared modules, LCSC.

**Process:**
- on-demand, plus an optional bounded task `CANDLE12_V3_BTC_OPSVIEW_Hourly` at HH:10 UTC (needs approval);
- the time is outside OOS-2 bar close (HH:00–HH:02) and HH:15–HH:35.

**Budget:**
- BelowNormal priority;
- < 5 s CPU, < 150 MB RSS, < 30 s wall (hard kill at 60 s);
- refuses when commit headroom is < 1.5 GB or the OOS-2 heartbeat is > 7 min old;
- no network apart from the local database.

## 7. Optional: OOS-2 store backup (separate approval)

- **What:** a daily byte copy of the OOS-2 store to a backup folder at 03:10 UTC, with a sha256 manifest. Copying bytes is not parsing.
- **Who reads what:** Track 2 reads only the manifest's time and hash-check result. The backup is sealed under the same rules as the store.
- **Status:** not part of V1 unless approved.
